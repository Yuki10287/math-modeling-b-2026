# 第三问联合调度：本轮实现与验证

## 结论

在冻结后、未参与开发调整的60组配对条件中，联合调度候选版把平均总虚拟时间从 **3070.21秒降至3036.68秒**，平均省 **33.53秒（1.09%）**。40组更快、20组更慢，最差退步102.12秒，最好节省216.19秒。两版均完成全部清除并通过独立证书审计。

这是一个幅度有限的平均改进，适合作为下一轮对照候选，不能称为全面替代当前版本的突破。第四问未开展。本轮没有操作官方模拟器，也没有把五份官方演练日志补造为新策略的反事实回放。

原 `solver.py` 的 `lean` 代码与原手动入口均保留。本轮候选入口为 `joint_solver.solve_multi`，默认配置 `route_interleave`。直接把候选模型纳入现有程序的调用方式见文末。

## 1. 最后保留了哪些模型变化

### 1.1 测向后重新调度，保留未完成任务

旧版选择一个源后，通常会连续定位、清除该源，再安排下一个任务。新版允许每完成一次主局部动作，就根据最新信息重新安排已知源和剩余扫描任务。

信息状态继续包括源的位置外包集合、各未知频道尚未排除的区域、机器狗位置和当前频道。现在还明确保留被暂缓源的光学覆盖路径及累计局部步数。测过源A之后，如果新路线更适合先处理B，可以先去B，随后再回到A；这不丢弃A已有的测量证据。已经开始的有限光学覆盖不会因为切换任务而重置。

这属于允许任务暂停和恢复的滚动调度。执行一次动作后重新规划，与一次执行完整个当前源的服务流程不同。它有利于把新的定位信息用于全局安排，但也可能增加频道切换、机会测量和计算量，因此必须比较整局总时间。

### 1.2 扫描点同时考虑进入和离开的路程

将仍需排除的格子分配给保证覆盖它们的扫描任务。格子中心集合为C，格子半对角线为ρ，则该扫描点的可靠位置集合为：

\[
K(C)=\bigcap_{z\in C}B(z,1000-\rho).
\]

给定路线上的前一点a和后一点b，在K内寻找使 `||q-a||+||q-b||` 较小的位置；末尾扫描则只考虑进入路程。原来主要沿原扫描站与某一个锚点的连线移动，现在可以在整个二维可行域中选择位置。

投影子问题使用二维圆盘交集的约束生成：最优候选来自单个圆的径向投影或两个圆的交点，再用全部约束复核。路程目标采用有限次投影迭代和开放路径重排，始终保留之前的可行方案。投影在边界上增加微小内退，防止不同浮点运算让相切格失去覆盖。

当前规划的代理路程不会因接受一个坐标更新而变长，所有剩余格仍有计划中的覆盖。这只是**当前代理规划**的性质，不保证在未知未来反馈下整局用时不增加；源的位置代理点也不是源的真实坐标。

### 1.3 完成条件与行动证书继续使用实际反馈

- 未知频道只有在实际收到无信号后，才更新负观测覆盖。
- 未来计划覆盖不算作已经完成的覆盖。
- 定位测点仍使用原有接收检查；清除和有限光学覆盖仍需通过连续区域检查。
- 各源累计局部动作达到30步后进入原有恢复流程；暂停和恢复不会重新获得30步预算。
- 最终仍需16个成功清除，或“成功清除频道＋可靠排除频道”完整覆盖20个频道。

## 2. 试过、但没有进入当前候选配置的方向

本轮没有将所有新增机制一并打开。主要开发版本的源码快照，以及实验配置、轨迹和失败记录保留在 `results/joint-dev-*` 中。

| 开发分支 | 模型变化 | 观察与取舍 |
|---|---|---|
| route | 只调整扫描点的进入、离开路程 | 平均有小幅收益，但不能单独解决源服务顺序的问题 |
| joint | 给局部测量增加剩余搜索成本评分，并选择兼顾搜索的测点、清除落点 | 部分场景明显节省，但增加测量、出现退步；未作为默认配置 |
| flex | 扫描点移动时重新分配重叠区域的覆盖责任 | 普通开发条件平均更快，但稀疏开发条件平均慢4.81%，最差慢515.31秒，未采用 |
| fused | flex加局部搜索成本评分 | 稀疏开发条件仍平均略慢，未采用 |
| interleave | 每次动作后重新调度，扫描点沿用旧策略 | 稀疏开发条件较好，普通开发条件平均慢0.99% |
| route_interleave | route与每次动作后重新调度结合 | 两类开发条件均平均更快，冻结后进入独立验证 |

特别是joint/fused中的评分使用“新增扫描为无信号”的分支估计后续覆盖成本。它只用于候选排序，实际执行仍按真实反馈处理，但它没有完整评价发现新源的各个分支，不能当作准确的期望总时间。直接联合“局部动作与覆盖”的思路仍值得研究，本轮数据尚不支持把这个近似版本加入最终候选。

## 3. 冻结后的独立对照

开发选择完成后，先写入 `results/joint_selection.json`，记录配置、源码指纹和预定验证种子，再运行留出测试。留出结果出来后未调整模型。原版与候选版使用完全相同的源布局、固定位置误差场及计费规则。

| 布局类型 | 独立布局数 | 配对条件数 | 原版均时/秒 | 新版均时/秒 | 平均变化 |
|---|---:|---:|---:|---:|---:|
| 普通分布，源数10—16 | 12 | 36 | 3136.59 | 3093.99 | 降低1.36% |
| 10源稀疏，接收半径1000米 | 4 | 8 | 2873.90 | 2853.91 | 降低0.70% |
| 10源接近圆域边界，接收半径1000米 | 4 | 8 | 3346.91 | 3354.87 | 增加0.24% |
| 10源集中在单侧，接收半径1000米 | 4 | 8 | 2691.08 | 2643.35 | 降低1.77% |
| 合计 | 24 | 60 | 3070.21 | 3036.68 | 降低1.09% |

普通分布每种布局测试smooth/hash/extreme三种误差场，其余每种布局测试smooth/extreme两种。它们都是自行规定的测试分布，不代表官方生成分布。共享布局的多个误差场不被当作独立布局样本。

按布局成组、按分布分层的10000次bootstrap，平均节省时间的95%区间约为 **12.53—58.11秒**。该区间只描述这些自建分布下的不确定性，不能外推为官方成绩的置信区间。

60次候选运行清除684个源实例；同一源布局在不同误差场下重复计为实例，不能说成684个独立布局。原版60次也全部完成。

## 4. 时间到底省在哪里

| 指标 | 原版 | 新版 |
|---|---:|---:|
| 平均移动时间/秒 | 2271.69 | 2237.34 |
| 平均测量次数 | 120.27 | 120.45 |
| 最后清除后的平均查漏时间/秒 | 175.21 | 203.79 |
| 本机平均求解计算时间/秒 | 3.02 | 4.41 |
| 本机最大求解计算时间/秒 | 6.34 | 9.11 |

平均移动时间减少34.35秒，几乎解释了全部总时间收益。平均测量次数几乎不变，而计算量有所增加。部分批次在同一台机器上并行运行，墙钟时间受机器负载影响，不能视为官方程序运行时间。

尾段查漏平均反而增加约28.58秒，说明“最后清除后还花多少时间”不能单独作为目标。新版某些场景更早完成清除，然后继续查漏，最终总时间仍可能较短。

## 5. 验证边界

另外9个确定性特殊场景全部通过，包括原点重合源、远处重合源、16个边界源、末尾远源、双簇、共线、5/20/1000米阈值、密集源与角度量化边界。两版各清除108个源实例；候选在7个场景更快、2个略慢。这组平均降低7.61%，但其构造具有明显针对性，不能替代上面的60组留出统计，也不与之合并宣传。

所有138次对照运行（原版69次＋候选69次）都通过了独立计时、公开观测一致性、连续覆盖证书、位置集合包含真源及完整光学路径检查。求解器只获得位置、当前频道、测量和清除四项接口，源真值只供环境与事后审计使用。69次候选中累计清除792个源实例。

新增几何代码通过圆盘交集解析案例、随机可行域检查、进出路程检查和覆盖规划不修改证据的检查。新启动入口也通过临时本地HTTP替身测试，包括首次测量响应丢失后重试不重复计费、指令序列与直接调用求解器完全一致。测试使用系统分配的临时端口，没有连接官方模拟器端口。

开发中一个route案例曾记录224.8秒的墙钟耗时；对同一案例进行性能剖析重跑约6.7秒，输出总虚拟时间一致。异常原始记录保留，不用于替换或筛选留出集数据。

## 6. 如何使用与后续建议

本地运行示例（在本目录执行，输出目录须尚不存在）：

```powershell
python -X utf8 benchmark_joint.py --start-seed 8700 --seeds 2 --fields smooth,hash,extreme --schedules lean,route_interleave --split development --out results/my-joint-check
python -X utf8 test_joint_planning.py
```

程序调用：

```python
from joint_solver import solve_multi
result = solve_multi(public_api, trace=[])
```

若之后由你手动做官方演练，候选入口是 **`运行第三问联合调度版.cmd`**。输入队号和端口后，由你在模拟器中手动启动第三问演练，等待倒计时结束，再回到启动窗口确认；日志前缀为 `q3-joint-`，配置记录为 `route_interleave`，还会记录新增代码的指纹。旧的 `运行第三问.cmd` 仍运行lean，便于对照。

建议把这个版本作为下一轮对照候选，保留旧版。当前收益只有约1%，一次官方演练的布局差异可能大于这个幅度；不要凭两个不同布局的总时间就认定模型胜负。

若继续研究，重点应转向更准确的“源服务成本＋剩余搜索成本”估计，尤其是边界布局，以及完整评价未知频道出现正信号后的新增任务成本。当前最有价值的结论是：调度方式确有改进空间，但仅把覆盖几何放宽、或把单一无信号分支收益加到局部评分上，并不能稳定带来更快的整局表现。

证据文件：`results/joint_selection.json`、`results/joint_holdout_summary.json`、`results/joint-holdout-*/cases/`、`results/joint-stress/`、`results/joint_http_validation.json`。全部模型与验证代码的冻结指纹核验通过。
